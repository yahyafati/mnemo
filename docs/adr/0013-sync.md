# ADR 0013: Sync between devices

- **Status:** Accepted on the defaults of `docs/sync/ROADMAP.md`, which the owner confirmed on 2026-10-03
  (the **(owner)** points below stand as written). The desktop half of the Google spike has run and is recorded
  below; the Android half needs a device and is under "Still open".
- **Date:** 2026-10-03
- **Context for:** `docs/sync/ROADMAP.md` (S0–S8); ADR 0005 (secrets), ADR 0009 (licence and distribution),
  ADR 0010 (desktop); ARCHITECTURE §6

## Decision

Devices of one user sync through **storage the user owns**: a folder first, Google Drive second, WebDAV
optionally. There is **no Mnemo server**, and the SQLite file is **never** copied between devices. Each device
writes its own numbered **change files** and reads the other devices' files; the merge runs on each device.

### Why no server, and why not copy the database

- A server is an operating cost, a privacy promise to keep and a target; `PROJECT_OVERVIEW.md` §6 already chose
  "file-based sync through user-owned storage". A self-hosted Mnemo server is out of scope.
- Copying the database file loses one device's reviews when both studied offline (last copy wins), and SQLite
  files in a folder that a sync tool is copying are a known way to corrupt a database (journal and `-wal` files
  travel separately).
- **Change files** have one writer each: a device only ever creates files under its own `devices/<id>/`, so the
  backend needs no locks, has no write conflicts and works on anything that can list, read and write files.

### Remote layout (S2 records the final version here)

```
<root>/
  sync.json                               # format version, collection id, created at, encryption salt + check
  devices/<deviceId>/device.json          # name, platform, app version, last seq, the seqs it has applied from others
  devices/<deviceId>/changes/<seq>.mnc    # a batch of changes, written once, never rewritten
  snapshots/<deviceId>-<clock>.mns        # the whole collection as of a clock value (S4)
  media/<sha256>                          # media files, written once
```

`sync.json` is written once by the device that creates the location. `device.json` is the only file ever
overwritten, and only by its own device. Every other name is unique or content-addressed, so one name always
means one content. Every file carries a **format version**; a device that reads a newer one stops with "Update
Mnemo on this device to keep syncing" and rewrites nothing it cannot read.

*As built (S2, `:core:sync`):*

- **Flat stores.** A path is made of `[A-Za-z0-9._-]` segments under `sync.json`, `devices/`, `snapshots/` or `media/`
  and has no `__`. `DocumentAccess` lists files but not subfolders, and Drive's file names are flat too, so the
  folder backend keeps the whole layout in one folder with `/` written as `__`
  (`devices__<id>__changes__3.mnc`). Anything else in the folder (`.DS_Store`, a sync tool's "name (1)" conflict
  copy) is not a valid path and is never listed.
- **The envelope.** Every file except `sync.json` is `"MNSY"`, a 16-bit format version, a flags byte (encrypted,
  zstd-compressed), a 32-bit body length, the body, and the SHA-256 of everything before it. The version is read
  first, so a newer format is refused (`SyncUnsupportedVersionException`) before anything else is checked. The
  length and the checksum are how a half-written or damaged file is told from a whole one: it is never applied
  (`SyncCorruptException`), and one that is *shorter than its header says* is flagged `maybeIncomplete`, because a
  write that is still going on looks the same. The body is compressed first (not for media), then encrypted.
- **`sync.json`** is plain, indented JSON: `formatVersion`, `collectionId`, `createdAt` and, when encrypted,
  `encryption` (`kdf`, `iterations`, `salt`, `check`). Unknown fields are ignored, so a later step can add some
  without a new version. `device.json` holds `deviceId`, `name`, `platform`, `appVersion`, `lastSeq`, `applied`
  (device id → newest seq applied) and `updatedAt`. A change file holds `deviceId`, `seq`, `clockFrom`, `clockTo` and
  the changes, each `{type: "put" | "delete", table, id, clock, fields}`; the device and seq in a file must match its
  name.
- **No atomic write.** There is no rename in `DocumentAccess`, so a write isn't atomic and a crash can leave a
  partial file under the final name. `SyncRemote` replaces such a remnant when the same device writes the same
  name again (only the owning device writes its names; media are content-addressed, so a replacement is the same
  bytes), and never replaces a whole file or one it can't read. A provider that renames a name clash
  ("name (1)", as Android's tree access does) is detected and undone, so "exists" holds there too.
- **Caps.** A change file is cut at about 2 MB (compressed, encrypted); one change bigger than that stays alone in
  a file. A file may not decompress to more than 256 MiB.
- **Where the in-memory store lives.** `InMemorySyncStore` is in `:core:sync`'s main source, not `:core:testing`:
  `:core:testing` depends on `:core:data`, which will depend on `:core:sync`, and every module that tests syncing
  needs the store.

### Ordering: a hybrid logical clock

`updatedAt` is wall-clock time for a whole row, so it cannot order two edits to different fields, and a phone with
a slow clock would lose to what it has already seen. Sync adds a **hybrid logical clock** (`SyncClock`):
`now() = max(wall clock, last + 1)` and `observe(remote)` moves `last` past a remote value. A change is stamped
with the clock when it is *packed*, not when it is made, and each device keeps the clock of every field it has
written or applied (`sync_field_clocks`). Ties are broken by device id. No merge rule reads the local wall clock.

> A's clock is a day ahead. A edits a note's front (clock T+1d). B syncs, observes T+1d, and edits the same front:
> B's change is stamped after T+1d and wins on both devices. Without `observe`, B's edit would be older than A's
> and silently lost.

### Merge rules (S3)

All rules are deterministic: two devices that have seen the same change files end up with the same rows,
whatever order the files arrived in. Per table:

| Data | Rule |
|---|---|
| Review logs | Union by id. Only `deletedAt` (an undo) ever changes. |
| Card schedule | One unit. One side reviewed since the last common review → that side's schedule. Both → **replay** (below). |
| Card flags, `deckId`; notes (per field, `tags`, `hint`, `deckId`); decks; note types | Per field, last writer by stamp. A note's `fields` list is compared per position. |
| Deletes | Delete wins over a concurrent edit. |
| Two decks, same parent, same name ignoring case | The lower id wins; the other's notes and cards move to it and it is soft-deleted, as normal changes. |
| Media | Union; the file is uploaded before the change that references it. |
| `ai_answers` | Last writer per `(noteId, kind)`. |
| Scheduling settings | One record, last writer, travels as a pseudo-table with the fitted FSRS weights. |

**Per field.** A edits a note's front, B edits its back, both offline: both edits survive. If both edit the front,
the later clock wins on both devices.

**Replay.** Review logs are facts, schedules are derived from them. A card reviewed on both devices offline has
two histories; the merged schedule starts from the schedule after the newest review both devices have (from the
`stateAfter`/`stepAfter`/`dueAfter` snapshot S1 adds to the log) and applies every later live review in
`reviewedAt` order through FSRS with the receiving device's synced settings. Fuzz is seeded from the card id and
`reps`, so every device computes the same result. Undone reviews are skipped.

> Card C is due. A answers *Good* at 09:00, B answers *Again* at 09:05, both offline. After syncing both hold two
> review logs and the same schedule: C after *Good*, then *Again*, which is what one device would have produced.

**Delete wins.** A deletes a note, B edits it. After syncing it is deleted on both. The edit is not lost from the
log, but there is no resurrection. A note or card that arrives in a **deleted deck** (B added a card to a deck A
deleted) restores the deck as `<name> (recovered)` so new work is never hidden. **(owner)** The alternative is
that the deletion wins and the new cards are deleted with the deck; recovery is proposed because losing an hour of
card-making is worse than one extra deck.

**Replay seam.** `:core:data` cannot see `:core:domain`, which holds `StudyScheduler` and its model ↔ FSRS mapping.
Decision: `:core:data` defines `ScheduleReplayer`, and `:core:domain`'s `domainModule` binds it to
`StudyScheduler`. The mapping stays where it is, and tests for the merge use a fake replayer plus one test with the
real one.

*As built (S3, `:core:data/sync`, schema v7):*

- **One round** is `SyncEngine.sync(remote, device, announceSettings)`: pack the outbox into change files (media files
  first), read the files of the other devices that this one has not applied, apply them in one transaction, pack what
  the merge itself wrote, write `device.json`, fetch missing media. Files are applied in the order of their first
  change's clock, then device, then number. The engine neither schedules itself nor takes a lock (S4's
  `SyncRepository` does), and it needs `sync_state.enabled = 1`.
- **Stamps.** A change is stamped when it is packed, with one clock value for the whole run (a device's runs are
  numbered, so its own stamps never tie); the stamp is `(clock, device id)` and the larger wins. This device keeps the
  stamp of every field it has written or applied in `sync_field_clocks`: per column, per *unit* (a card's eight
  schedule columns are one) and `*` for "the whole row, at its insert", so an import of 12,000 cards is not a quarter
  of a million rows. A change is applied to a field only if its stamp is newer than the field's own **and** the row's
  `*`; the same file applied twice, or two files in either order, give the same row. `updatedAt` is stamped like a
  field. `createdAt` keeps the earliest value and `deletedAt` the earliest non-null one (a row that any device deleted
  stays deleted). A write that changes only `updatedAt` is not recorded by the S1 triggers, so such a write (saving
  a deck under its own name) can leave `updatedAt` different on two devices; nothing reads it for a decision.
- **A note's `fields` merge by position** (scenario 2: the front on one device, the back on the other). The change
  says which positions it made, found by comparing each text's hash with `sync_field_clocks.base`, the hash as of the
  last sync; the receiver replaces a position only if the stamp is newer and the text was not edited here since.
  `tags`, `hint` and the other columns are whole values.
- **A change that arrives before its row** (a sync tool may deliver a device's files in any order, and two devices'
  files in any order) is kept in `sync_field_clocks` with its value and applied when the row's insert arrives. A file
  of a device that arrives after a newer one of the same device is still read: `sync_seqs` keeps, per device, the
  newest number applied and the numbers below it that were missing (a window of 200). A file that cannot be read yet
  (`SyncCorruptException`) stops the run for that device and is reported as `blocked`; the next run tries again.
- **A field with a local change that is not sent yet** is left alone when a remote change arrives for it; that change
  is stamped after everything seen here and wins anyway.
- **Replay** (`CardReconciler`). Review logs carry the schedule they produced, and `repsAfter` counts a device's answers
  1, 2, 3 …; a log that does not continue the one before it in `reviewedAt` order (its `stateBefore` is not the other's
  `stateAfter`, or its count is not one more) was given without it. The answers from there on are replayed on the schedule
  after the last one both have, through `ScheduleReplayer`, which `:core:domain` binds to `StudyScheduler`. A card that
  starts over (a new card after a longer history) is not a fork. With no fork, the answers newer than the card's last
  review are replayed on the card (the schedule is behind a log). The outcome is written as an ordinary local change, so it
  reaches the devices that did not compute it, and a device that computes it too writes the same values. Logs without a
  schedule (Anki imports, rows from before v6) never take part. **Known limit:** B answers on top of A's answer while A
  undoes it before syncing. Every log is kept and the devices agree, but the schedule is B's, computed on top of the
  undone answer; undo restores the card but the answer on top of it cannot be told from a valid one without the schedule
  *before* each answer, which the log does not hold.
- **Decks.** Two live decks with the same parent and name (ignoring case) are merged after every apply: the lower id
  stays, the other's notes, cards and subdecks move to it and it is deleted. Work in a deleted deck is moved to
  `<name> (recovered)`, a deck whose id is derived from the deleted deck's, so every device that does this makes the
  same one; cards of a deleted note are deleted. All of it is written with the triggers on.
- **Media.** The file goes up before the change files of the run, by hash, and a media row that arrives without its
  file is fetched on this and later runs; until then it is "missing media" in the report and the card shows the
  placeholder. A hash from a change file is checked before it becomes a file name.
- **Scheduling settings** are the pseudo-table `settings`, one record stamped as a whole. The first run of a device that
  did not create the location records its settings as a baseline and sends nothing, or it would overwrite what it is
  about to receive; the creating device passes `announceSettings`. The record last synced is kept in the stamp's
  `value`, which is how a local change is noticed.
- **Cost.** 12,000 imported cards (24,001 changes, two files): packed and written in about 1.6 s and applied in
  about 1.3 s on the desktop (2.1 s and 2.1 s in the Robolectric host tests), in `SyncMergeTest`.

*As built (S4, `:core:data/sync`; no schema change):*

- **`SyncRepository`** (`DefaultSyncRepository`, a Koin `single`) is the lifecycle: `status`, `syncNow`, `create`, `join`, `rejoin`,
  `uploadAsNew`, `unlock`, `leave`, `deleteSyncData`. One mutex: `syncNow` returns `Busy` while another round runs, the
  rest wait. Where a device syncs is a `SyncBackend` (a folder today) opened by `SyncStores`; the location is remembered
  in `<files>/sync/config.json` (`SyncConfigStore`), **outside** the database and preferences so a restore never brings
  another device's idea of it, and the passphrase's key in `SecretStore` (`SecretIds.SYNC_KEY`, which `pruneOrphanedKeys`
  leaves alone). `enabled` (database) + config (file) give the states: neither = Off, config without `enabled` =
  `Restored` (what `PendingRestore` leaves, since it sets `enabled = 0` and the file stays), both = on.
- **Snapshots** (`SyncSnapshots`) are JSON lines, streamed, so a large collection is never one tree: a header, the writer's
  `sync_seqs` (what it has applied per device, with late files), the scheduling settings with their stamp, the media
  files nothing referenced, every `sync_field_clocks` row, then every row of every synced table. Loading one is
  copying the writer's state: rows, stamps and positions are replaced in one transaction, the clock moves past
  everything in it, the settings are adopted. It has to carry the **stamps**, not one stamp per row: a late edit of a
  field the snapshot has at a newer stamp must still lose, and one of another field must still win.
- **Create** needs an empty location (`SyncAlreadyExistsException` otherwise), uploads this device's media (the change
  files only carry rows), runs a first round that announces the settings, and writes the first snapshot. Any failure
  undoes it (config, key, `enabled`, the files it wrote). **Join** reads the newest snapshot, refuses (with
  `SyncReplacesLocalDataException`) to replace a collection that has live decks or notes until the caller confirms,
  saves that collection with `BackupManager` to `<files>/sync-backups/` (newest three kept), writes its own
  `device.json` (with exactly what the snapshot covers) **before** changing anything, so no clean-up can decide it
  needs nothing, loads the snapshot and runs a round. That first round reads this device's own change files after the
  snapshot's position too (`includeOwn`): a device that joins again may find files of its own that the snapshot
  predates, which the others have applied. A first round that can't reach the location doesn't undo the join.
- **Leave** turns sync off, clears the outbox, stamps and positions and the config and key, and, if it can reach the
  location, marks its `device.json` as old (`updatedAt = 0`) so the others stop waiting for it. **Delete sync data**
  removes every file (the manifest last, so a half-done delete is found and finished by trying again), then leaves.
- **Restore** is two choices from `Restored`: `rejoin` (the location's data again, the restore discarded, after a backup)
  or `uploadAsNew` (empties the location and creates it again, with a new collection id; the other devices find the
  id changed at their next round, report `Replaced` and rejoin).
- **Maintenance** (`SyncMaintenance`, at most hourly): a device writes a snapshot once 50 change files are newer than the
  newest one, announces it in its `device.json` (`DeviceInfo.snapshot`: what it covers) and keeps the newest two.
  A change file is deleted only if the newest snapshot has it **and** every device whose `device.json` is newer than
  90 days has applied it (its `applied` and its `gaps`, both in `device.json`); a device with no readable
  `device.json` stops the clean-up. A media file is deleted once it has been unreferenced for 30 days: a store can't
  say how old a file is, so snapshots carry the time each unreferenced file was first noticed.
- **A device away too long** is found only when its last round is older than the 90 days: it then checks whether change
  files the newest snapshot covers, and that it hasn't applied, are gone. A file that is merely late in a folder can't
  look like that, because a clean-up never deletes what an active device hasn't applied. The report is
  `SyncProblem.MustRejoin`; nothing is merged until the user rejoins (which replaces the collection, after a backup).
- **Running by itself** (`SyncAutomation`): a round when sync turns on or the app starts, and one 5 seconds after the last
  edit (`SyncDao.observeChangeCount`, debounced; every answer is an edit, so this is also "after a session"). The
  rounds while the app is closed are `SyncBackgroundWork`: unique periodic WorkManager work with a network
  constraint every 3 hours (`SyncWorker`, which always succeeds: the status says what failed) on Android, a timer in
  the application scope every hour on the desktop. `MnemoApplication` and `openCollection` start the automation.
- **Limits:** a snapshot is one file built in memory as bytes (tens of MB for a very large review history) and one
  upload. A backend that can't take that needs chunked uploads (Drive's resumable upload covers it, S6).
- Tests: `SyncLifecycleTest` (create, join, join with data and its backup, encrypted locations and a lost key,
  leave, delete, clean-up that keeps what a recent device needs, an unknown device, a device away too long and one
  that is away but missing nothing, restore both ways, a device that joins again and its own files).

*As built (S5, `:feature:settings`, `:feature:decks`, `:shell`; no schema change):*

- **Screen.** Settings › Sync is its own route (`SyncRoute`), opened from a row in Settings. `SyncViewModel` turns the
  repository's lifecycle into one state (`SyncUiState`: status, pending changes, encryption, devices, the open dialog, a
  notice) and dialogs: create (optional passphrase), join (passphrase if the location is encrypted; a second question when
  it would replace a collection with data), unlock, join again, upload as the new sync data, leave, delete. A set-up
  call that fails keeps its dialog open with the `SyncProblem`. Passphrases live in call arguments only (and, for the
  join-over-data question, in one field of the ViewModel); never in the state, `SavedStateHandle` or logs. A new
  passphrase is at least 8 characters and repeated (`SyncPassphrase`).
- **Repository reads.** `inspect(backend)` decides between create and join without changing anything; `isEncrypted()`
  comes from the config file; `devices()` reads each `device.json` (skipping a corrupt one and one with `updatedAt = 0`,
  which is how a device that left says so). `Throwable.syncProblem()` is public so a screen can explain any failure.
- **Attention.** `SyncStatus.attentionFrom()` says from when the user should be told: at once for `Restored` and for every
  problem a person has to fix, a day after the last good round for `WaitingForNetwork` and `Error(Other)`. The Decks
  banner (`DecksViewModel.syncBanner`) is a flow that waits out the remainder instead of polling; no banner while sync works.
- **Folder hint** is the capability `syncAppFolders` (desktop only): a phone's picker reaches those apps' folders
  unreliably (see S2's notes on Drive's document provider), so it only says to pick an empty folder.
- **Limits.** The folder can't be changed while syncing (stop and set it up again). A folder store lists only Mnemo's own
  file names, so unrelated files in the chosen folder are neither seen nor touched; the create dialog says to use a folder
  of its own. Dialogs with text fields have no Robolectric test (the platform limit in CLAUDE.md); their logic is in
  `SyncViewModelTest`.

*As built (S6, Google Drive; `:core:sync/google`, `:core:data/sync`, `:app`; no schema change):*

- **Store.** `GoogleDriveSyncStore` is a `SyncStore` over Drive REST v3 and OkHttp, in the app-data folder only (`spaces=appDataFolder`,
  `parents: ["appDataFolder"]`). Layout flattened like the folder store (`/` → `__`). Drive allows two files of one name, so a
  create looks for the name first, and for `sync.json` (the one name two devices write with different contents) the older of two
  claims wins and the loser deletes its own; other names are one device's own or named by their content. Each file carries an
  app property `g` (`devices`, `snapshots`, `media`, `root`), so listing `media/` or `devices/` is one filtered query, not the whole
  folder. A file is created in one multipart request, or in a resumable session above 5 MB (8 MB chunks; a failed chunk asks Drive
  how much arrived and goes on, three times; the session address is only used on the upload host and gets no token); Drive makes
  the file when the last byte arrives, so a cut-off upload leaves nothing. Errors: no network → offline; 401 → one new access
  token, then auth; 403 → quota (`storageQuotaExceeded`), slow-down (retried, as 429 and 5xx, with 0.5/1/2/4 s pauses) or auth;
  404 → not found. Redirects are never followed.
- **Sign-in.** `GoogleSignIn` (PKCE S256, a random `state` checked before anything else, `access_type=offline`, `prompt=consent`)
  uses the platform's `OAuthAuthorizer` (a seam in `:core:sync`): `AndroidOAuthAuthorizer` sends the system browser an `ACTION_VIEW`
  and receives `<package name>:/oauth2redirect` in `OAuthRedirectActivity` (`:app`, a no-display activity), passed on through
  `OAuthRedirectHub`; `DesktopOAuthAuthorizer` listens on `127.0.0.1:<random port>` with a plain `ServerSocket` (no `jdk.httpserver`
  in the runtime), answers one page, ignores other requests and times out after five minutes. **AppAuth was not needed**: the
  Android half is one intent and one activity. Scope is `drive.appdata` only (no `email`/`openid`: the screen says "Google Drive",
  not an address, so the only Google data read is Mnemo's own folder). A grant without that scope, or without a refresh token, is
  refused.
- **Tokens.** The refresh token is `SecretIds.GOOGLE_REFRESH_TOKEN` in `SecretStore` (a reserved id); the access token is in memory
  (`GoogleAccessTokens`, refreshed a minute before it expires). `invalid_grant` is the auth error: the Sync screen shows "Sign in
  to Google" (`SyncRepository.signInToGoogleDrive`, then a round). Leaving or deleting the sync data signs out: the token is
  removed first, then revoked at Google (best effort).
- **Build config.** `MNEMO_GOOGLE_CLIENT_ID` becomes `BuildConfig.GOOGLE_CLIENT_ID`; the desktop's id and secret go into
  `mnemo-google.properties`. `GoogleClientConfigSource` (`:core:data`, bound by `:app` and `:desktop`) is null without them, and
  `SyncRepository.googleDriveAvailable` then hides the option. Runbook: `docs/sync/google-setup.md`.
- **Backend and UI.** `SyncBackend.GoogleDrive` (stored as `gdrive` in `config.json`, no secret in it). Encryption is on by default
  in the create and upload dialogs when the location is Drive (the owner can switch it off). Strings that said "folder" are neutral
  or have a Drive variant.
- **Not done / left for the owner.** The Android half of the spike (the custom-scheme redirect on a device, and whether the token
  exchange needs no secret) and the first real round trip with the owner's clients: nothing here ran against Google. The tests run
  the store against a fake Drive on MockWebServer (`FakeDriveServer`, the `SyncStore` contract, paging, resumable upload and resume,
  the refusals above) and the sign-in against a fake token endpoint. Drive's listing is eventually consistent, so a file written a
  moment ago may be missing from the next listing; the engine already treats a late file as late.

### Recording changes (S1)

Every local write must be recorded without any repository remembering to. SQLite **triggers** on every synced table
fill a `sync_changes` outbox (`tbl`, `rowId`, changed column names, `at`); an update trigger records only columns
whose value changed. They catch Anki import, Smart Extract's accept and bulk browser actions too. Triggers are
skipped while `sync_state.applying = 1`, so applying remote changes does not echo them back, and while sync is off
(`WHEN` on `sync_state.enabled`), so users who never turn sync on pay nothing but the table. Undo becomes a **soft
delete** of the review log, because a hard delete leaves nothing to send. The **device id** (a random UUID, in
`sync_state`) is not part of a backup restore, so a backup restored on a second device does not pose as the first.

*As built (S1, schema v6):* an insert is recorded as `*` and an update as the comma-separated names of the changed
columns (`createdAt` and `updatedAt` are never listed); a composite key (`ai_answers`) is `noteId/kind`. The
triggers are generated from one list of tables and columns that a test compares with the real tables. A review
log also records the whole schedule its answer produced: `stateAfter`, `stepAfter`, `dueAfter`, and
`repsAfter` and `lapsesAfter`, because the fuzz seed uses the review count, so a replay that starts from a log
needs it. `PendingRestore` reads this device's id before it swaps the database files, writes it into the restored
file and turns sync off; a device with no database of its own, or a backup from before v6, ends with a new id.

### What syncs and what never does

**Syncs:** decks, note types, notes, cards, review logs, media, saved AI answers and the scheduling settings
(retention, limits, steps, fitted FSRS weights).

**Never syncs:** API keys, provider records, models, routes and usage (a provider without its key is useless, and
keys never leave the device, ADR 0005), OAuth tokens, the WebDAV password, the sync passphrase's key, appearance,
the reminder, backup settings, onboarding. Secrets stay in `SecretStore`, never in Room, logs, backups or a
change file. **(owner)** Say if anything on the "never" list should sync (appearance is the usual candidate).

### Joining, leaving, restore, and what v1 does not do

- **Create** writes `sync.json` and a snapshot into an empty location, and refuses one that has `sync.json`.
- **Join** is either an empty device that downloads the newest snapshot and the change files after it, or a device
  with data that makes a backup (`BackupManager`) first and is then **replaced**.
- **Leave** turns sync off on this device and keeps the collection; deleting the location's files is a separate,
  confirmed action.
- **Restore** from a backup turns sync off and asks: upload this collection as the new sync data (naming the other
  devices in the confirmation), or join again and discard the restore.
- **Compaction**: a device writes a snapshot after enough change files; files older than the newest snapshot are
  deleted only once every device seen in the last 90 days has applied them. A device away longer must join again
  and is told so. Remote media nobody references and older than 30 days goes at the same time.
- **Not in v1:** merging two unrelated collections (a device that has data and joins a location is replaced, after
  a backup), sharing decks between people, a Mnemo server or AnkiWeb, syncing AI providers, choosing which decks
  sync. **(owner)** The first of these is the one users will ask for; it is left out because a correct deck-level
  merge of unrelated histories is a project of its own.

### Encryption

Files are encrypted end to end, **on by default for Drive and WebDAV** (the provider can read the files
otherwise) and **optional for a folder**. No new dependency: `javax.crypto` only.

- Key: **PBKDF2-HMAC-SHA256**, 600,000 iterations, a random 16-byte salt kept in `sync.json`, 256-bit output. The
  derived key (not the passphrase) is stored in `SecretStore` on each device. *As built:* the passphrase is
  NFKC-normalized (so "é" typed as one character or two is one passphrase), UTF-8 encoded and hex-encoded before it
  reaches PBKDF2, because what PBKDF2 does with a password's characters is up to the security provider (the JDK
  uses UTF-8, Android's providers have differed) and a passphrase with an accent must give every device the same
  key. The count is accepted between 1,000 and 10,000,000 when read, so a hostile `sync.json` can't hang the app.
- Files: **AES-256-GCM**, a random 12-byte nonce per file in front of the ciphertext, with the file's path and the
  format version as associated data, so a file moved or renamed on the backend fails to decrypt.
- `sync.json` holds a **check value** (a known constant encrypted with the key), so a wrong passphrase fails at
  once on Join, not as a corrupted file later. `sync.json` itself is not encrypted.
- **Not encrypted:** file names (ids, sequence numbers and clocks, no content) and their sizes and times. Media
  files are encrypted too, by hash of the plaintext in the name, so a provider can tell whether two users have
  the same image. **(owner)** Accept this, or name media files by a keyed hash (costs a lookup table).
- **Passphrase loss is final**: nobody, including the owner, can read the sync data. The help says: leave, and
  create the sync data again from a device that has the collection.

The iteration count is stored in `sync.json`, so it can rise later without breaking old locations.

### Backends

`SyncStore` (`:core:sync`, pure JVM, no Room, no Android): `list(prefix)`, `read(path)`, `write(path, bytes)` for
new files only, `overwrite(path, bytes)` for the device's own `device.json` only, and `delete(path)`. Failures are
`IOException` subclasses (`SyncException`) that tell **offline, auth, quota and not found** apart (and "already
exists" and other I/O errors; the format layer adds corrupt, unsupported version and passphrase). Calls block, for
an IO dispatcher. A store never follows redirects
and takes its base URL as a constructor parameter, so tests use MockWebServer or a temporary folder.

1. **Folder** (`FolderSyncStore` on `DocumentAccess`; S5). On the desktop the folder may sit inside Google Drive
   for Desktop, Dropbox, Nextcloud or Syncthing. A file is written under a temporary name and renamed where the
   platform allows, and a half-written file is detected by length and checksum and ignored.
2. **Google Drive** (S6), REST v3 over OkHttp.
3. **WebDAV** (S7, optional), over OkHttp, HTTPS only except local addresses by the `AiEndpoint.check` rule.

### Google Drive: scope, clients and what the desk research found

- **Scope `drive.appdata`.** Google lists `drive.appdata` and `drive.file` as non-sensitive scopes, which need
  basic app verification and not the security assessment that restricted scopes (full Drive) need. `appdata` is a
  hidden folder only Mnemo can read, which is what a sync location is. What Google's documentation says about it:
  the folder is not visible in the Drive UI, the user *can* delete it manually (the app must treat "not found" as
  "the sync data is gone"), nothing in it can be shared or trashed (a delete is permanent), and it is deleted when
  the user uninstalls (disconnects) the app from their Drive. It counts against the user's own Drive storage; the
  page does not give it a separate quota, so a full Drive is the "quota" error. **Decision: `drive.appdata`**,
  not `drive.file`, since `drive.file` shows files in the user's Drive that they can then rename, move or delete
  by accident.
- **No Google libraries.** No Google Sign-In, Play Services or Google client library (ADR 0009, `LicensesFlowTest`).
  Sign-in is OAuth 2.0 in the browser with **PKCE and a `state` check** (Google makes PKCE mandatory for native
  clients).
- **Desktop (spike run 2026-10-03, Desktop-app client, project `mnemo-510516`).** Loopback redirect
  (`http://127.0.0.1:<random port>`) with PKCE (S256) and a `state` check works: the redirect carries `code`,
  `iss`, `scope`, `state`. **Google's token endpoint rejects the exchange without the client secret**
  (`400 invalid_request, client_secret is missing`) and so does the refresh, even with PKCE, whatever the
  documentation's "optional" suggests. With the secret both succeed and a refresh token is returned
  (`access_type=offline`, `prompt=consent`); the access token lives about an hour. Google calls this secret
  not confidential for installed apps, but a GPL desktop binary can be unpacked, so: the secret is **build
  configuration** (`MNEMO_GOOGLE_DESKTOP_CLIENT_ID` / `…_SECRET` from the environment or `local.properties`, never in
  the repository, a CI secret for releases), and a build without it hides Drive. It is not stored in a user's
  `SecretStore` and the privacy text does not call it a secret of the user's. One `drive.appdata` round trip worked
  with that token: create (multipart, `parents: ["appDataFolder"]`), list (`spaces=appDataFolder`), read
  (`alt=media`), delete (204), then an empty list. After `revoke`, a refresh fails with
  `400 invalid_grant, Token has been expired or revoked.`, which S6 maps to the "auth" error.
- **Android.** Google deprecates the loopback redirect for Android client types and **disables custom URI schemes
  for new Android clients by default**, steering apps to Google Identity Services, which is Play Services and so
  excluded here. The documented escape is the "Custom URI scheme" switch under *Advanced settings* of the Android
  client, which keeps AppAuth-Android (Apache-2.0) with a custom-scheme redirect workable. An Android client is
  bound to the **package name and the signing certificate's SHA-1**. The owner has created the Android client
  (its downloaded JSON has a client id and no secret, as Google documents for Android clients). **Still to
  confirm on a device: that the custom-scheme redirect with AppAuth completes, and that the token exchange needs
  no secret.**
- **F-Droid.** F-Droid re-signs APKs with its own key unless the build is reproducible and published with the
  developer's signature, so the SHA-1 registered for the owner's key will not match an F-Droid build and Google
  will refuse it. Expected outcome, **to confirm**: the Drive backend is **hidden in F-Droid builds** (the recipe
  gets no client id; the folder backend and WebDAV work there). **Decided by the owner (2026-10-03): hidden in
  F-Droid builds**, with no anti-feature in the recipe. Showing it with `NonFreeNet` stays the alternative if a
  client type that does not need the SHA-1 ever works.
- **Client id handling.** `MNEMO_GOOGLE_CLIENT_ID` (and the desktop client's values) are read at build time from
  the environment or `local.properties`, like the signing settings in `ReleaseConfig.kt`; they are never in the
  repository. Without them the Drive option is not shown, so forks and builds without them still work and never
  use the owner's quota or consent screen.
- **Tokens.** The refresh token goes in `SecretStore`, the access token stays in memory. A revoked or expired
  token becomes the "auth" error and Settings asks to sign in again. While the consent screen is in *Testing*
  status, Google expires refresh tokens after seven days (from Google's general OAuth policy, not from the pages
  read here), so Drive must not ship before the app is verified and published.
- **Verification takes time.** The consent screen needs an app name, home page and privacy policy (the pages in
  `scripts/pages`), and Google's review can take weeks. **(owner)** Start it as soon as this ADR is accepted if
  Drive is wanted.

## Consequences

- Sync works with anything that stores files, and a user who wants no cloud can use a USB-synced or LAN folder.
- Android and the desktop share one merge engine and one format. Version rules in the format keep an old device
  from damaging newer data.
- Every synced table carries triggers and the outbox; with sync off the cost is a `WHEN` test per write, and one
  small table.
- Review replay means two devices that studied the same card offline get one schedule that neither would have
  shown at the time of the review. This is the price of never losing a review.
- Moving to a new phone later needs either the passphrase or a backup; encryption on by default makes forgetting
  the passphrase the biggest support risk.
- `:core:ai` is no longer the only network client: `:core:sync` makes requests to Google Drive and WebDAV servers
  (ARCHITECTURE and the privacy policy change with S5 and S6).
- The Drive backend depends on a Google review, a consent screen and a client id that forks do not have; the
  folder backend does not, and is first for that reason.
